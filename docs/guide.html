Programming
with Mithril

Write plain scalar code. Mithril finds independent work in the program and runs it across CPU cores or on a GPU.

Its syntax is a Python subset, with functions, loops and values. The compiler and runtime handle task splitting, shared computation and result collection, so you can compose the algorithm in one source program.

The camera stays fixed while the spheres move in depth and height. Their apparent sizes, shadows, reflections and refraction change with each pose.

def main():
    n = size()
    img = array_new(n * n, 0)
    for y in range(n):
        for x in range(n):
            img = array_set(img, y * n + x, pixel(x, y))
    return (n, n, img)

The loop computes the image one pixel at a time in source. You select a device and thread count when running it; the workload examples show how those calculations can overlap.

Arrays are values: array_set returns an updated array while existing readers of the previous version retain its contents. That gives parallel execution a precise result to preserve.

What changes from C or Rust?

C and Rust give you control over memory, execution and the libraries used to build a parallel program. Mithril places more of those decisions in its compiler and runtime. The practical difference is how much machinery you write around the computation.

DecisionIn a C or Rust implementationIn Mithril
Splitting independent workChoose a threading library, task API or GPU kernel structure.Write the dependencies; generated code and the scheduler expose eligible work.
Reading shared dataChoose ownership, lifetimes and synchronization appropriate to the implementation.Values can be shared; the runtime tracks their storage and consumers.
Updating a valueChoose mutation, copying or a persistent data structure.The update produces a new value. Uniquely owned storage can be reused.
CPU and GPU executionChoose portable libraries or maintain device implementations.Compile the same supported source to the CPU or NVIDIA GPU backend.
Low-level controlDirect access to layout, SIMD, device APIs and a large systems ecosystem.Work within the language’s value model and the execution forms its compiler supports.

C and Rust can express these algorithms too. Mithril derives more of their execution structure; the measurements below show what that costs and saves on specific workloads.

Compared with writing CUDA

With CUDA, you decide how a computation maps to GPU threads and blocks—groups of threads that can cooperate. You can choose memory spaces and synchronization around that mapping. For a pixel batch, the mapping can be straightforward:

// CUDA work-mapping sketch; device pixel() and host setup omitted.
__global__ void render(uint32_t *out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n * n)
        out[i] = pixel(i % n, i / n);
}

Mithril takes the render loop shown above and chooses its execution structure. A CUDA implementation gives you direct control over that structure and can use hardware-specific instructions. When the algorithm reveals uneven or recursive work, CUDA may require additional task management; Mithril supplies a general scheduler. That convenience carries runtime costs which an optimized kernel can sometimes avoid.

Compared with functional languages

Immutable values and shared computation are familiar ideas in functional programming. Haskell can defer evaluation until a value is demanded; OCaml supports functional data structures alongside mutation. The distinguishing questions are how parallel execution is requested, how sharing is represented, and which guarantees are checked.

Mithril represents computation as an interaction net (IN): connected nodes transformed by local rules. The rule diagram shows how those local steps permit different execution orders.

LanguageRelevant modelHow Mithril differs
Haskell / GHCNon-strict evaluation; parallel strategies specify how pure values should be evaluated in parallel.Mithril derives eligible tasks from program dependencies and represents shared computation with net rules. Lazy evaluation and deterministic parallelism also exist in Haskell.
OCaml 5Domains and task libraries let the programmer create parallel work and await results.Mithril generates the task structure from supported computations. OCaml gives the author task APIs alongside its wider language and runtime facilities.

Which programs benefit?

Follow the work through a few familiar algorithms. Which calculations can start together? Which need an earlier answer? What data do they share?

Rendering: each pixel has its own calculation

In the tracer above, the colour of pixel (0, 0) depends on rays through that pixel and the scene. Pixel (1, 0) traces different rays through the same scene. Neither calculation needs the other pixel’s colour:

a = pixel(0, 0)
b = pixel(1, 0)
c = pixel(2, 0)
return (a, b, c)

All three calls can proceed together. Only the returned tuple needs their completed results. The full image repeats this pattern across thousands of pixels, giving workers a supply of independent jobs. A pixel containing glass may take longer than one looking at a plain wall; workers can take more available work as they finish.

This is an independent batch. Ray tracing gives each job enough calculation to make distributing it worthwhile. If each job were just one addition, managing the jobs could cost more than running those additions locally.

Merge sort: split, solve, combine

To sort a large list, merge sort divides it into two smaller lists and sorts each one. Both sorting calls have their own input, so they can proceed together. They keep splitting until the lists are small enough to sort directly.

The merge waits for both sorted lists. It repeatedly takes the smaller of their next elements: 1, then 3, then 6, then 8. This creates an alternating pattern of independent work and combination steps. Each level offers a different amount of parallel work; the merging still takes time.

This shape is called divide and conquer. Mithril’s sorting example expresses the two sorting calls as arguments to a merge. Its list-based split and merge have sequential work, which limits the benefit of adding more cores.

Queen search: a choice opens separate possibilities

Suppose you want to place four queens on a 4 × 4 board so none attack each other. Put the first queen in column 0 and search for legal positions for the remaining queens. You can also start with the first queen in column 1, 2 or 3. Each starting position defines a separate search; it needs no answer from the others.

Within a search, each legal placement opens further choices for the next row. An illegal placement ends that branch. The amount of remaining work becomes clear as the search proceeds, so different branches can take different amounts of time. For this small board, the four starting columns yield 0, 1, 1 and 0 solutions. Their counts combine into the final answer: 2.

This is a branching search. Independent partial-board searches can run together; each search follows its own dependencies.

Nearest-neighbour queries: many searches share one index

Imagine a collection of points on a map. For each new location, you want to find the closest stored point. A k-d tree organizes the points into smaller spatial regions, so a query can skip regions too far away to contain a better answer.

Build the tree once. A query near one location and a query near another can then search it independently. Both read the same tree; each keeps its own closest point and distance found so far.

Inside one query, the search visits a nearby region first. Its result determines whether a farther region is worth visiting. Those visits have a dependency. Across queries, a sparse area may need few visits while a crowded area needs many, giving the scheduler jobs of different sizes.

This combines shared read-only data with an independent batch. Mithril’s k-d tree example passes the same tree to paired batches of queries. Each query follows its own dependencies while other queries proceed. This pattern also occurs when many inputs are checked against the same rules or lookup structure.

A number sequence: each step produces the next input

For a Collatz sequence, divide an even number by two; replace an odd number with three times that number plus one. Repeat until reaching 1:

def steps(n):
    count = 0
    while n != 1:
        if n % 2 == 0:
            n = n // 2
        else:
            n = 3 * n + 1
        count = count + 1
    return count

Starting at 6 gives 6 → 3 → 10 → 5 → 16 → 8 → 4 → 2 → 1: eight steps. To choose the operation after 3, the program first produces 10. To choose the next one, it first produces 5. Each iteration needs the preceding iteration’s output.

This is a serial chain. Extra workers cannot run these successive iterations together. Efficient local execution matters here. Sequences starting at 6, 7 and 8 are independent of one another, however, so a batch of sequences offers parallel work between chains. Loops and recursion can contain either shape; the dependencies decide.

What the spatial-tree C comparison shows

For the shared spatial index described above, the single-thread C implementation takes 0.333 seconds, Mithril at one thread takes 0.406 seconds, and Mithril at sixteen threads takes 0.090 seconds. Distributing the queries produces the multicore gain; one-thread Mithril has overhead.

Where Mithril gains over these Rust programs

Mithril can distribute independent recursive work across cores and share retained computations across closure calls. You write the ordinary calls; the compiler and runtime supply that execution structure. In Rust, you can build the same behavior with a task library and explicit shared values. The advantage is less execution machinery to write, with performance depending on the program’s shape.

The shared-graph program takes 0.27 seconds on sixteen Mithril threads versus 1.67 seconds in the single-thread Rust twin: about 6.2× faster through automatic task distribution. Mithril at one thread takes 1.91 seconds, so the gain comes from using more cores. A parallel Rust implementation has not been measured here.

The pipeline benefits from sharing each stage’s configuration-dependent setup across calls. Its Rust twin repeats that work inside boxed closures; Rust can recover the same saving by computing and capturing the setup explicitly. The closure example shows how this happens.

Rust wins on the serial recurrence, and the persistent map has similar timings without a multicore gain. The closure interpreter is a large Mithril loss: each call needs new work, while closure copying and reduction add overhead. Choose Mithril when distributing recursive work or sharing closure setup simplifies your computation; these results establish no general speed advantage over Rust.

How can execution order change safely?

The glass shader gives a useful example. It traces a reflected ray and a transmitted ray, then combines their colours. Each ray calculation can finish independently; the combination waits for both.

# From glass(); surface geometry and the total-reflection branch omitted.
mirror = trace(add(p, scale(n, eps())), reflect(d, n), depth - 1)
through = trace(sub(p, scale(n, eps())), rd, depth - 1)
return add(scale(mirror, f), scale(through, 1.0 - f))

In the interaction net, nodes connect through points called ports, including one principal port. Two principal ports joined together form an active pair. A rewrite rule replaces that pair and reconnects its surrounding wires. One such replacement is a reduction step.

For example, an erasure node connected to a number means the number has no consumer. The rule removes the pair. Other rules apply a function, compute an operation, select a branch or distribute a shared value.

In the modeled core rules, different active pairs occupy separate nodes and their reductions commute. This local diamond property gives confluence: terminating reduction paths agree on a final net. The scheduler can choose between independent reductions while preserving that result.

The grouping of the expression remains fixed. Splitting a fold, such as summing an array in chunks, changes grouping and needs an additional proof: the operation must be associative and have an identity such as zero for addition, under its actual numeric representation.

The proof and test table identifies the modeled rules and production checks. A program must still reach a final value.

How the hybrid model executes the program

Mithril uses the rule model at two times. During compilation, it reduces everything it can with the known inputs. The remaining computation is the residual program. During execution, native code performs suitable parts of that residual, while net and task machinery handle sharing and independent work.

Before specialization

def square(x):
    return x * x

def pick(c, a, b):
    if c > 0:
        return a
    return b

def shade(n):
    return square(n) + pick(1, square(3), n)

Remaining computation

def shade(n):
    return n * n + 9

The known condition selects the first argument. The constant multiplication produces 9. The multiplication using n waits for the caller’s value.

This is specialization: evaluating a program with partial knowledge of its inputs. Removing the known work reduces what every later invocation must execute. Mithril prefers to do this through its interaction rules, so constant evaluation, branch selection and call unfolding compose as steps of the same computation. Compilation budgets keep reduction bounded and retain unfinished work in the residual.

Lowering then turns the residual into efficient execution forms. Short arithmetic sequences benefit from machine instructions and registers. Allocating net nodes, dispatching rules and moving data for each tiny operation would add cost to a largely fixed dependency chain.

A native scalar function can run arithmetic directly. A function that opens independent branches receives code that can run locally on a work budget, then suspend at supported points and offer unfinished work to the scheduler. Its continuation stores the code and state needed after the results arrive. A join collects those results, as in the colour example.

A closure or tuple produced by a net can still contain pending values. The bridge waits for required fields before compiled code consumes them, and delivers results from compiled calls back into waiting net wires. This keeps the execution forms accountable to the computation represented by the net.

Where INs help most

Nets make dependencies, sharing and unfinished work explicit. They support partial evaluation during compilation, preserve shared computation under closures, and provide state that can be inspected or saved for later reduction. Their local rules also supply independent units of work for the reducer.

Sharing can change how much work gets done

A closure is a function that retains values from where it was created. In this pipeline example, stage(c) returns a function that uses configuration c for every later input x.

def stage(c):
    return lambda x: (x * 3 + setup(c)) & 1048575

setup(c) depends on the retained configuration, while the multiplication depends on each new input. Mithril’s sharing rules let the setup work run once and remain shared across applications of the same stage.

That explains the pipeline result in the Rust table. Its Rust twin keeps the setup call inside boxed stage closures. A Rust implementation can explicitly compute and capture the setup value; the comparison measures the source-shaped program, rather than the fastest implementation of the idea.

The closure interpreter has the opposite shape. Almost all its work depends on the new environment passed to each call. Copying and reducing that closure tree gains little reusable work, while the runtime cost remains. That explains its large loss in the Rust table.

Mithril supports functions, branches, loops, tuples, user-defined data types, closures and arrays. Integers are signed 56-bit values with wraparound; floats default to f64, with f32 elaboration for supported operations. The syntax resembles Python, and the numeric and value semantics are Mithril’s.

The build instructions include the GPU requirements. The generality corpus provides shared graphs, persistent maps and closures to inspect. The design notes are the reference for implementation details and open work.
