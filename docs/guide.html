Chapter 0

The whole system in one picture

A program's meaning is a set of rewrite rules on a graph. The compiler runs those rules early on whatever does not depend on input, then turns what is left into native code for the CPU and the GPU. The runtime runs the same rules on the rest.

Net lens

A program is a graph of small agents. Computation is rewriting pairs of agents. The compiler and the runtime do the same thing, at different times.

Compiler lens

A conventional pipeline (parse, IR, optimize, lower, codegen), with one change: the optimizer is not a list of passes, it is the language's own evaluation rules run early (partial evaluation).

reference lens

reference takes a Python-like program to C with a parallel runtime and was our performance baseline. Mithril keeps the rules as the definition of meaning and uses them as the optimizer too.

Chapter 1

Four rules you already know

An agent is a small node with ports. One port is its principal port (orange dot); the others are auxiliary. A wire connects two ports. When two agents touch principal port to principal port, they form an active pair, and exactly one rule says what they become. That is the whole machine.

principal portactive pair (the wire that fires)agent

Mithril's full table has these agent kinds (crates/mithril-core/src/port.rs, Tag): numbers and floats, constructors (Con, for tuples and data), Dup, Era, Lam/App (closures), Op, Swi (if on a number), Mat (match on a constructor), Ref (a named function) and Ext. The runtime adds Kont (a hand-off to compiled code) and Arr (an array block).

Net lens

Each rule looks at exactly two agents and replaces them locally. No rule ever needs to see the rest of the graph.

Compiler lens

Think of an SSA dataflow graph where every value is used exactly once. Using a value twice needs an explicit copy node (DUP); dropping one needs a drop node (ERA). Evaluation is local rewriting of that graph.

reference lens

This is the same family of model reference's lineage (HVM, interaction combinators) is built on. Mithril's table is its own, sized for a compiled language: numbers, tuples, matches and named functions are first-class agents.

Chapter 2

Why order never matters

Every agent has exactly one principal port, so an agent can be in at most one active pair. Two active pairs therefore never share an agent, and firing one cannot disturb the other. Any order of firing, including all at once, reaches the same result. This property is called confluence, and it is where Mithril's parallelism comes from.

Net lens

Locality plus one principal port per agent means active pairs never overlap. That single structural fact is the guarantee.

Compiler lens

Like a pure dataflow graph with no shared mutable state: independent nodes can run in any order and on any thread with no data races. The difference is that here it holds for the whole language, including calls, branches and sharing, not only for arithmetic.

reference lens

The same property is what lets reference promise parallelism without annotations. Mithril uses it twice: to parallelize at runtime, and to justify running the rules early in the compiler, since early firing cannot change the answer.

Chapter 3

The optimizer is the rules

At compile time each function body becomes a net whose inputs are unknown wires. Every rule that does not need an unknown fires. What remains, the residual, is read back as code. Step through a real run on this program:

# learn.py
def sq(x):
    return x * x

def pick(c, a, b):
    if c > 0:
        return a
    return b

def main():
    n = array_len(array_new(5, 0))   # unknown at compile time
    return sq(n) + pick(1, sq(3), n)
$ mithril net learn.py
function  rewrites  calls  ops  before  after
sq               0      0    0       3      3
pick             0      0    0       6      6
main            10      0    1      13     12

$ MITHRIL_NET_CORE=1 … (residual main)
n = array_len(array_new(5, 0))
return n * n + 9

Net lens

The compiler reduces the net until only redexes that wait on input remain, then reads the net back as Core. No pass knows what "inlining" is.

Compiler lens

Partial evaluation by the language's own semantics. A striking check: a small interpreter applied to a constant program specializes to that program's arithmetic (the first Futamura projection), with nothing in the compiler knowing it is an interpreter.

reference lens

Our reading of reference is that its compile-time optimizations are conventional compiler work before a parallel runtime. Here the net is the optimizer of record: a Core-level rewrite that duplicates what a rule does is not allowed (CLAUDE.md).

Chapter 4

How nets become fast code

The residual is not interpreted. Each function is emitted in the forms its callers need. The fastest form is plain native code; the others let work suspend, split across workers, or cross back into the net. Below is the real output for learn.py (CPU, Rust).

Native form s_: plain machine code

// main: n*n + 9, ints pre-shifted by 8 bits
fn s_2(ctx, fuel) -> i64 {
  let v0 = arr_new_raw(5, 0) as i64;
  let v1 = arr_len_of(v0 as u64).wrapping_shl(8);
  let s3 = v1.wrapping_mul(v1.wrapping_shr(8));
  let s2 = s3.wrapping_add(2304);  // 9 << 8
  free_val(ctx, v0 as u64);
  return s2;
}

Other forms of the same function

// d_: dive form, runs natively under a budget
fn d_2(ctx, fuel) -> R { *fuel -= 1; Ok(retag(s_2(ctx, fuel))) }
// x_: rule form on boxed values, delivers to a record
fn x_2(ctx, parent) { …; deliver(ctx, parent, t4); }
// fc_: the CALL rule's entry, when a call is a task
fn fc_2(ctx, a, b, aux) { dive_to(ctx, 2, &[aux]); }
Net lens

Lowering is a faster way to reduce a region of the net. It must compute exactly what reducing that region computes, bit for bit, and any region can fall back to the rules.

Compiler lens

ANF, type inference, unboxing and native scalar forms, then two printers (Rust, CUDA) from one LIR. A suspended call is a CPS continuation made explicit as a record with a pending count; a dive is a direct-style call with a budget.

reference lens

Fork sites derived from the net, suspension on an empty budget as the fork mechanism, borrowing and reuse: these are Mithril's own (§14 review). The ports we measure against are reference's benchmark programs.

Chapter 5

Where parallelism comes from

One runtime model on both devices: tasks are pending rule firings, records are continuations waiting for values, dives run native code under a budget. The CPU and GPU differ only in how they pick what to run next.

Net lens

Parallel work is simply several redexes fired at once. Confluence says it cannot change the result, so the scheduler is free to choose.

Compiler lens

A work-queue runtime with explicit continuations. Buckets are per-rule work queues; a record is a join counter plus its frame. Determinism comes from the model, not from locks.

reference lens

The device scheduling policy (grow/work rounds, the parallel and sequential worlds) was adopted from the reference paper and is marked for replacement. The CPU wave scheduler, records and dives are Mithril's own.

Chapter 6

reference, and how we differ

reference (reference, version 2.0.31 as measured here) compiles a Python-like language to C with a parallel runtime, on the CPU and on CUDA. Mithril was built with reference as the performance baseline. The rule is: reference is measured, its runtime source is not read to design Mithril's.

Chapter 8

What is not done yet

  • The GPU lane. Faster than 16 CPU threads on 8 of 17 programs by wall clock, behind reference's GPU on most. Root-cause investigation in progress.
  • One rule-table source. The device carries a hand-written copy of the rules, held equal by tests only.
  • Proof. Confluence of the rule table is argued, not machine-checked (Lean: not started). Folds are Lean-checked.
  • Two optimizations outside the rules. tail_inline and if_convert are Core rewrites with thresholds: a drift from "optimizations are rule firings", listed for fixing.
  • Known bug. An array of tuples built inside a closure is read wrongly by compiled code (pinned by an ignored test).
